# 小海 AI 事项预填助手

用户在小海里说明要办的事（意图明确但内容模糊也可以）、上传材料，Dify 工作流整理出业务表单需要的字段，再返回一条预填链接。浏览器扩展打开用户已经登录的学校业务系统，在页面内填写字段和附件，最后停在“提交”按钮前，由用户本人核对和提交。

目前支持学生请假和科研论文登记。当前扩展版本为 `0.4.4`。

## 新架构和解决的痛点

学校业务系统大多没有可用的业务接口，登录状态又只能留在用户浏览器中。同时，论文题目、作者、日期这类字段不能只靠 AI 推断。新架构主要解决三个问题：

1. 业务系统填写放到用户浏览器里完成，不把学校 Cookie 或会话交给服务端。
2. Dify 负责理解材料，字段校验和最终提交仍由业务规则与用户把关。
3. 新增业务时可以复用链接协议、页面跳转、任务暂存和附件下载，不必重新写一套。

整体链路：

```text
小海 / Dify
  理解需求、抽取字段、校验数据
        |
        v
apply-prefill.v1
  统一携带 serviceId、表单数据、附件和过期时间
        |
        v
浏览器扩展 worker
  解析链接、暂存当前标签页任务、处理附件、原地跳转
        |
        v
事项注册表 + 业务适配器
  根据 serviceId 找到目标页面并填写对应表单
        |
        v
学校业务系统
  用户核对后自行点击“提交”
```

不同内容放在不同位置，后续修改范围比较清楚：

| 要改的内容 | 修改位置 |
| --- | --- |
| 事项 ID、目标网址、页面范围 | `shared/service-registry.js` |
| 业务页面注入范围 | `manifest.json` |
| 表单字段和页面操作 | 新增一个 `xxx-filler.js` |
| 新页面附件读取和写入 | `worker.js` |
| 字段归一化、Dify 工具和预填链接 | Dify 插件 |
| 用户需要提供哪些材料、如何追问 | Dify 工作流 |
| 所有业务共用的链接协议 | `shared/prefill.js` |

## 当前能力

### 学生请假

从小海确认请假类型、日期、事由和附件后，扩展进入学生请假应用，填写请假信息并上传证明材料，不自动提交。

### 科研论文登记

支持从论文 PDF 中提取标题、作者、期刊、发表日期、收录信息等字段，也支持会议名称、会议地址、分区和影响因子。扩展按学校页面步骤完成预填和附件装载，到达完成登记页后停止自动流程。

## 快速运行

浏览器扩展：

1. 打开 `chrome://extensions` 或 `edge://extensions`。
2. 开启开发者模式。
3. 选择“加载已解压的扩展程序”，加载 `hainanu_apply_assistant-0.4.4`。
4. 更新代码后先点击扩展的“重新加载”，再刷新学校业务页面。

Dify 侧安装对应的 `.difypkg`，并在 provider 凭据中确认 `prefill_base_url` 指向小海预填页面。

## 新增业务的整体流程

新增一个业务时，建议按下面的顺序做。不要先写工作流，后面再临时调整表单字段，否则返工会比较多。

### 1. 先做预填条目

先整理业务表单真正需要哪些字段，再把用户说法、材料内容和学校页面字段做成一张对照表。可以借助 AI 从页面截图、DOM 信息或现有表单中提取候选字段，但最终要人工确认：

- 字段中文名和 `serviceId`
- 学校页面的 `name`、`id` 或 `data-field`
- 字段类型：文本、下拉、单选、复选、日期、附件
- 中文选项对应的学校 ID
- 哪些字段必填，哪些字段可以留空
- 哪些字段必须由用户确认，不能让 AI 推测

这一步得到的是稳定的数据契约。后面的适配器、Dify 插件和工作流都按它传递字段。

### 2. 编写业务适配器

在扩展中新增 `xxx-filler.js`，只负责当前业务页面的填写。它要处理表单等待、字段写入、下拉选择、日期控件、附件入口和页面异常。

适配器只处理自己的 `serviceId`。多步骤表单要保存任务级状态，避免用户返回上一步后又被自动拉回最后一页。最终“提交”按钮不能点击。

### 3. 更新浏览器扩展

主要包括：

1. 在 `shared/service-registry.js` 注册事项、目标地址和页面范围。
2. 在 `manifest.json` 增加需要注入的页面。
3. 把新适配器加入 `content_scripts`。
4. 如果涉及新附件字段或新域名，同时调整 `worker.js`，不要直接放开任意 URL。
5. 更新 `manifest.json` 的扩展版本号并重新打包。

### 4. 更新 Dify 插件

在 `apply_codec.py` 中注册新事项，并编写字段归一化逻辑，把 Dify 提供的中文枚举转换成学校页面使用的 ID。简单业务可以先通过 `application_prefill` 生成预填链接；需要独立参数表单时，再增加专用工具。

新增或修改工具 YAML 后，要重新打包 `.difypkg` 并安装到 Dify。

### 5. 创建对应工作流

工作流负责业务判断，不负责页面选择器。一般按这个顺序组织：

1. 接收用户描述和附件。
2. 从 PDF、图片或文档中提取文字。
3. 用 LLM 按固定 JSON 结构抽取字段。
4. 用代码节点校验必填字段、日期、枚举和附件。
5. 信息不完整时向用户追问；完整后调用 Dify 预填工具。
6. 输出字段摘要和预填链接。
7. 在最终回复中提醒用户核对，并自行提交。

### 6. 联调和验收

至少检查以下内容：

- 链接能被 `shared/prefill.js` 正确解析。
- `serviceId` 只进入对应适配器。
- worker 只打开一个业务页面。
- 未登录时完成统一认证后任务仍能继续。
- 刷新、返回上一步和重复点击不会重复填写或上传。
- 附件只上传一次，学校页面能显示上传结果。
- 其他业务的链接不会接管当前页面。
- 最终提交始终由用户本人点击。

## 接入原则

- 一个业务只使用一个稳定的 `serviceId`。
- Dify 传入的是已经校验过的业务字段，适配器不重新理解用户原话。
- 页面选择器以真实 DOM 为准，不要根据中文标题猜。
- 多步骤业务必须处理刷新、重入和“上一步”场景。
- 附件下载和写入要经过 worker，并保留域名、路径、大小和来源校验。
- 扩展只预填，不自动提交。
- 每次修改扩展或 Dify 插件都更新版本号，避免部署后无法判断用户实际安装的是哪一版。

## 安全边界

- 不读取、不保存、不上传学校账号密码。
- 学校 Cookie 只留在浏览器，不发送给 Dify。
- 附件只允许从受信任域名和路径读取。
- 新业务接入时同时维护 `manifest.json`、注册表和 worker 来源校验。
- 最终“提交”始终由用户操作。

## 当前限制

- 学校页面改版后，适配器里的选择器需要重新采集。
- Dify 工具、扩展适配器和附件处理之间仍有一部分枚举映射需要同步维护。
- 学生请假保留旧版消息和链接兼容逻辑，新业务优先使用 `APPLY_*` 通用消息。
- 出于安全考虑，当前不提供最终提交自动化，这是业务边界。
